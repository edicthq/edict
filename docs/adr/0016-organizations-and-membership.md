# Edict owns organizations, teams, members and invites

Refines [ADR 0014](./0014-better-auth.md): Better Auth keeps users, sessions, sign-in methods and the OAuth 2.1 provider, but its organization plugin is not used.

Organizations, teams, members, team membership and invites are Edict's own tables in `packages/db`, written through the org-scoped data-access layer. A member is either a human, linked to a Better Auth user, or an agent, linked to no user. Better Auth answers "who is this user", and Edict answers "what can this member do in this organization".

Better Auth's organization plugin covers the human half of this, but each of its tables breaks a decision we already made:

- Its `member` row requires a `user`. Agents are members without a sign-in identity ([ADR 0008](./0008-agents-are-members.md), [ADR 0015](./0015-oauth-connections-create-agents.md)), so we would have to create a fake user for every agent. Agents would then appear in the instance's user list, could hold sessions, and would blur the glossary's line between a user and a member.
- Its writes go through Better Auth's adapter in its own transactions. An invite accepted or a member removed could not write its event in the same transaction ([ADR 0005](./0005-transactional-event-log.md)), and the writes would skip the data-access layer that enforces `org_id` and sets the row-level security context ([ADR 0006](./0006-multi-tenant-from-day-one.md)).
- Its teams have no key, no privacy and no guest scoping, and its invites are email-only with no team list. We would carry most of the model in `additionalFields` and still write our own permission checks.

## Model

- **Organization**: name and slug. The tenant root, so it carries no `org_id` of its own.
- **Member**: `org_id`, kind (`human` or `agent`), role (Owner, Admin, Member, Guest) and, for humans, the user. A user is a member of an organization at most once. Agents can hold only Member or Guest; the extra powers an admin can grant an agent arrive with agents in M3.
- **Organization creation**: any signed-in user can create one and becomes its Owner. The instance's sign-up mode decides who gets a user in the first place.
- **Team**: `org_id`, name, team key unique within the organization, private or public.
- **Team membership**: a member in a team. Guests see only teams they belong to. Members see every public team and the private teams they belong to.
- **Invite**: `org_id`, email, role, the teams to join, who invited, expiry. The link carries a random token, and only its hash is stored. Accepting needs a signed-in user with the invited email, so a forwarded link lets no one else in. With SMTP off, an admin copies the link and sends it themselves.

Internal IDs are UUIDv7, generated by Postgres 18's `uuidv7()`. Better Auth's user IDs stay as Better Auth makes them.

The org-scoped API lives under `/api/v1` with Zod schemas in `packages/schema` ([ADR 0010](./0010-zod-schemas-drive-the-api.md)). Better Auth stays at `/api/auth/*`, unversioned.

## Considered options

- **Better Auth's organization plugin, with a fake user per agent.** Rejected for the reasons above. It would save the invite and role endpoints, which are a small part of this slice.
- **The plugin for humans, plus a separate agents table.** Every "who is in this team", "who can be a delegate" and "who did this" query would union two member tables, and the event log's actor would point at either one. The glossary already says a member is a human or an agent, so the schema should have one table for both.

## Consequences

- We write invite, role and membership endpoints ourselves, test-first over HTTP.
- An organization always has at least one Owner. Removing or demoting the last Owner fails.
- Removing a member keeps the row, marked removed, so events keep pointing at a real actor. A removed human can be invited back and becomes the same member again.
- Every write in this slice emits an event, so the event log table and its same-transaction helper land in this slice too.
- Row-level security covers members, teams, team memberships and invites from their first migration. One query has to cross organizations: listing the organizations a user belongs to. The members policy allows it by also matching the current user.
- When the domain rule and the instance's invite-only sign-up mode arrive, they extend the invite model and need no new decision.
